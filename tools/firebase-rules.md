# リーダーボード（Firebase RTDB）のルール適用手順

`tools/firebase-rules.json` の `rules` の中身を Firebase Console に貼り付ける。

## 適用手順

1. https://console.firebase.google.com/ を開き、`labolic-leaderboard` プロジェクトを選ぶ
2. 左メニュー **構築 → Realtime Database**
3. 上部タブの **ルール**
4. エディタの内容を、`tools/firebase-rules.json` の **`rules` キーの中身**に差し替える
   （`_comment` は貼り付けないこと。Console 側は JSON コメントを受け付けない）
   貼り付ける形は以下:

   ```json
   {
     "rules": { ... }
   }
   ```
5. **公開** を押す

## 適用後に必ず確認する

ルールを間違えるとスコア送信が丸ごと止まる。公開直後に実機で1回通すこと。

1. Pages 版でクリアまで進めるのは大変なので、**ルールタブの「Playground」**で先に検証する
   - 場所（location）: `/leaderboard/testkey`
   - 種類: `write`、認証: なし
   - データ: `{"clearDate":"2026-07-27","playerName":"test","fontClass":"f1","dayCount":42,"coins":1000}`
   - → **許可** になれば正常
2. 続けて同じ場所に2回目の write を試す → **拒否** になれば「既存の書き換え禁止」が効いている
3. `/leaderboard` に `read` → **許可**（ゲームが一覧を読むため）
4. 余計なフィールドを足したデータ（例: `{"foo":1, ...}`）→ **拒否**

その後、ゲーム本体からリーダーボード画面を開き、一覧が表示されることを確認する
（読み取りが壊れていないかの確認。書き込みは実際にクリアするまで試せない）。

## このルールで防げること・防げないこと

**防げる**

- 巨大な文字列や大量のフィールドを送りつけてDBを膨らませる行為
- 既存エントリの書き換え・削除（新規追加のみ許可）
- 想定外の階層（`/leaderboard` `/leaderboard_udm` 以外）への書き込み

**防げない**

- **フォークされたサイトからの書き込み。** RTDB のセキュリティルールは
  送信元の Origin や Referer を参照できない。「自分のドメインからだけ許可」は
  ルールでは表現できない
- 正しい形をしたスコアの捏造。`curl` で妥当な JSON を投げれば通る

つまりこのルールは**DBを壊されないための下限**であって、スコアの正当性は保証しない。
リーダーボードの性質上、ここは割り切る領域。

## 送信元を絞りたい場合（App Check）

ドメイン制限を本気でやるなら **Firebase App Check**（Web は reCAPTCHA v3 /
reCAPTCHA Enterprise）を使う。登録したドメインから来たリクエストにだけ
トークンを発行し、RTDB 側でトークンを必須にできる。

ただし**このゲームには実装コストがある**。現状は Firebase SDK を使わず
`fetch()` で REST エンドポイントを直接叩いているため、App Check を効かせるには
SDK（または App Check トークンを取得して `X-Firebase-AppCheck` 相当のヘッダを
付ける処理）の追加が必要になる。単一HTMLで完結している構成も崩れる。

フォークが実際に現れて困るまでは、上記の検証ルールだけで十分だと考えている。
